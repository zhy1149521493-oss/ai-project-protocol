## Decision and alternatives

| Option | Benefit | Cost/risk | Outcome |
| --- | --- | --- | --- |
| Request permission for each internal command/test/repair | Frequent checkpoints | Interrupts work already covered and discourages autonomous completion | Rejected by the user's explicit rule |
| Authorize a complete task within clear operations/assets/risks; reapprove only genuine increments | Enables efficient internal execution while preserving user control over material changes | Requires a clear boundary and honest classification of failures | Selected |
| Treat the complete-task phrase as unlimited permission or unlimited future rounds | Fewer pauses | Removes safety, asset and budget controls | Rejected; expressly outside authorization |

Section 1.5 now defines the task authorization and permits operation categories instead of enumerating commands. Existing user/task/approval evidence is cited rather than recreated as a per-action form. Reasonable internal choices and covered test failures proceed autonomously; evidence, finite resources and stop conditions still apply.

Permission expansion, uncovered global settings, unapproved protected assets, unapproved critical-route changes and over-budget work stop at the crossing operation. Actual dependent or inseparably risky work also stops. Other work continues only if already authorized, independently safe and within available budget; no unrelated work is invented merely to remain busy. If all remaining work genuinely depends on the pending decision, pausing all of it is appropriate.

Protected-asset deletion/movement, global network changes and driver/service installation retain their existing specific approval requirements. A prior explicit approval covering the same operation, assets and risks remains usable; a generic task, cleanup or repair goal cannot imply that approval. Platform/tool access restrictions are distinct from normal test failures and cannot be bypassed under this rule.

Cleanup is limited to identifiable task-temporary outputs, not user originals, deliverables or unrelated assets. Recovery requires an auditable original state/approved target and does not authorize additional global changes. Normal failures do not automatically cancel the task authorization or end the primary round.

## Separate dimensions and preserved constraints

- Authorization defines permitted operations, assets and risks; it can cover many internal actions.
- Main-instruction continuity and actual integrated results define conversation rounds under unchanged section 4.1. Internal agents, tools, parallel tasks, tests, retries and repairs do not add rounds.
- A genuinely independent later user engineering instruction still counts a new round. An existing task scope is not a reason to retrospectively merge completed rounds, invent a permanent engineering round or bypass required instructions.
- Budget and resource limits remain independent. A started fifth round may finish its authorized internal work under existing limits; a sixth requires approved extension. Task approval does not preapprove added rounds, additional resource rights or route changes.
- First-round complete-step delivery, five-round cap, extensions at most three, persistent issue/request counters, odd/even debate, major-route control, user participation/own-word understanding/second review, evidence, history and stop requirements remain.

## AI-added risk analysis and validation method

| Risk identified by AI | Control and paper check |
| --- | --- |
| Repeated approval requests manufacture a false blocker or extra rounds | Same covered test/repair/tool actions continue under one task; ordinary failure does not itself end the primary instruction |
| “Necessary” is used to enlarge protected assets or global effects | Check operations/assets/risks and prior approval; stop the actual increment before executing it |
| One local blocker halts an otherwise safe task | Identify real dependencies/risk coupling and continue only independent authorized work with budget |
| Task authority is mistaken for budget or platform permission | Test a new independent follow-up, exhausted budget, a permission-denied operation and a global-setting proposal separately |
| Cleanup/recovery destroys original or final assets | Check task ownership of temporary outputs and known restoration target; keep protected/unrelated assets outside generic cleanup |
| The new entry differs from the installed authority | Verify installed junction identity, current 1.3 dependency headers and relative links; do not make a copied rulebook |
