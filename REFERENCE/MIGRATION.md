# 候选审阅与版本迁移

当前交付 **2.0.0-rc1 是待审候选**。制作授权不是实例采用批准，也不等于发布新正式版。候选已发布到独立审查分支，仍不安装、不替换共享 Skill、不推送 GitHub 主分支，不读取或修改任何应用项目运行资产。

## 审阅

1. 先看 [新旧对应与取舍](CHANGE-MAP.md) 和 [验证记录](../docs/VALIDATION.md)，再完整读 [CORE](../CORE.md)、[ROUTE](../ROUTE.md)、[STATE](../STATE.md)。这里的空白未绑定状态不属于任何真实项目。
2. 旧版可在 [历史索引](legacy-1.3/README.md) 逐文件读取原文，完整包仍在 [legacy-1.3.zip](legacy-1.3.zip)。需要查历史时按目录原名读取所需条目，或解包到临时审阅目录；不要把旧入口再放入 Skill 搜索目录。归档中的规则只适用于旧版本，不与候选 CORE 竞争权威。
3. 正式采用前按当时有效的1.3制度和用户批准完成实际触发的审查，包括适用的三轮辩驳、用户理解核对及明确批准；不能用候选较轻的程序倒签旧版要求，内部复核/格式检查或外部意见不代替该过程。用户可批准候选、要求修改或拒绝；应明确是发布共享包还是迁移某个具体实例。现行实例继续遵守其已批准版本，不能因为候选更方便就提前采用其中部分审批规则。

## 将来获得采用批准后的步骤

- 核实实例的真实旧规则、完整路线/最终目标/验收、权限来源、现有工单与历史证据，而非用本包空表覆盖。保留旧文件和可核对快照/差异。
- 从旧单文件分离：规则进入实例 CORE，全部批准路线和验收进入 ROUTE，实时事实、W-ID/原指令/暂停或结单、U/A/Q/R、未解决P/B、授权/阻断及下一入口进入 STATE。所有正式决定和原始证据保留原位置或可追溯链接；批准事实不重新编造。
- 对每个步骤比较迁移前后 **C、U、A、Q、R** 和每个未解决问题的申请累计、旧成果/验收、授权边界；不能给旧步骤重新发5轮，不能借候选续接规则倒改已经结束的主轮，不能追溯声称旧版所需审查已完成。
- 标明待审批和未完成重大异议。采用后后续审查按明确生效范围执行；改变未完成申请的程序应在迁移批准中说明，不静默抹掉反对证据或批准条件。
- 在批准记录中写明采用版本、路径、范围、生效点和核对人。先在隔离副本完成拆分/链接/一致性检查，再在获准切换点更新入口；保存失败标未完成，继续使用最后一致的已批准版本，不能双写两套账。
- 旧路径保留可读兼容入口，明确当前的 CORE/ROUTE/STATE，旧历史仍可定位。共享包更新不自动迁移任何其他实例。
