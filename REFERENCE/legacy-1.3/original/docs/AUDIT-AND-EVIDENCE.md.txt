## Controlled counting revision 1.1

The budget measures independent primary engineering instructions between the user and the main agent, with their work process and integrated result. One primary instruction may include investigation, implementation, repairs, tests and independent internal review. Subagents, internal task splits, tools, reports and retries add no conversation rounds. Codex remains free to choose reasonable parallel collaboration within scope and resource/stop conditions.

A later independent user engineering instruction after the prior result starts a new round. If engineering must pause for a new user instruction or approval, the subsequent new engineering instruction also starts a new round; an administrative approval message alone does not. Instruction continuity, actual result submission and required user input determine the boundary, not task labels or report counts.

Conversation budget, internal workload, and actual resources/results are separate records. Default 5, extension maximum 3, persistent issue/request counters, odd/even review, major-route approval, user participation, full rereading and handoffs remain in force. No budget was added to an application project. Effectiveness gains remain untested.

## Controlled step-semantics clarification 1.2

The user's instruction clarified a reported interpretation ambiguity, which was not independently evaluated as an application incident here: a step is the complete task targeted by its first main engineering instruction, not a phase planned as five primary-development conversations. First-round execution includes the necessary investigation, implementation, integration, repair and initial validation within available authority and conditions. Later rounds address actual tests, defects/common causes, regression, acceptance gaps or bounded repair/retest of a genuine first-round blocker; no fixed second/third-round development schedule is introduced.

The local changes replace the weak definition in section 3.1, strengthen its planning/template fields, constrain follow-up purposes in section 4.2 and synchronize the user guide/skill. Required acceptance remains mandatory; when it is satisfied and no real work remains, stop early. An evidenced scale, dependency or authorization blocker is reported with remaining work/options, not hidden as planned development or false completion. The five-round cap, 1.1 counting and all existing approvals/stop conditions remain. [D-0002](decisions/D-0002-step-first-round-delivery.md) preserves the user's reasons separately from AI analysis and records the targeted checks. No application project evidence was independently inspected in this revision.

## Controlled complete-task authorization revision 1.3

The user's explicit revision establishes a complete, bounded engineering task as the authorization unit. Necessary covered investigation, implementation, internal agents/tools, testing, ordinary defect/related-issue repair and regression, identifiable task-temporary cleanup and recovery verification do not require repeated permission for each action. A normal test failure is not an authorization failure. The scope can use operation categories and asset/risk boundaries rather than a command-by-command approval list.

New engineering section 1.5 distinguishes scope, main-round counting, budget and platform/tool permission. Permission expansion, unapproved protected assets, uncovered global settings, unapproved major-route changes and over-budget work keep their existing approval gates. Stop the offending operation and actual dependencies; continue other independently safe work only within existing authorization and budget. Cleanup cannot silently include user originals/deliverables; recovery cannot invent a prior state. These clarify local execution, not blanket permissions or automatic future rounds.

[D-0003](decisions/D-0003-complete-task-authorization.md) records the user's wording, AI analysis, boundaries and paper checks. D-0001/2 remain frozen. Checks specifically cover same-scope repair without repeated approval, a stopped global/asset operation with safe work continuing, cleanup/recovery scope, new independent instructions and exhausted budgets.

## Concrete consistency repairs

The original audit supplied operational clarifications. The delegation-counting row now reflects the user's explicit 1.1 correction; that old interpretation is not retained as an active rule. Other entries remain scoped clarifications.

| Scenario and original ambiguity | Consequence | Delivered resolution and location |
| --- | --- | --- |
| One step is called a conversation, but also has a five-conversation budget | Primary development is planned across five conversations, or repairs become extra steps | First-round complete-step target; later actual tests/repairs/regression/acceptance or evidenced first-round blockers only, without spending unused rounds for their own sake: §§3.1, 4.2; D-0002 |
| Main agent delegates internal engineering tasks under one primary instruction | Counting internal tasks as conversations penalizes efficient parallel work | Count/reserve the primary round once, regardless of subagents or task splits; record workload and actual resources/results separately: §4.1; D-0001 |
| A task is approved, but each test, repair or tool command asks for approval again | Unnecessary interruption and artificial instruction/round boundaries | Apply the existing bounded task authorization; normal failures are repaired autonomously, genuine scope increments alone require the existing approval procedure: §1.5; D-0003 |
| Budget is exhausted and debate needs new experimental evidence | Circular dependency between approval and evidence | Request a bounded 1–3-round verification extension first; no automatic authority to implement a replacement route: §§4.2–4.4 |
| “Read-only investigation” or one long tool loop continues indefinitely | Scope or resource limits are bypassed | Bound the primary round and stop uninformative retries; internal investigation adds no rounds. After the authorized round ends, new engineering requires a primary instruction with available budget: §§3.3, 4.1–4.2 |
| A renamed route gets fresh default rounds | Historical effort and request sequence reset | Explicit old-to-new budget mapping; retain spent work and unresolved issue sequences; additional authorization must be explicit: §3.4 |
| Multiple issue sequences share an application | Choice of issue controls odd/even scrutiny | Increment each applicable established sequence; use highest scrutiny once; total extension remains at most 3: §4.3 |
| An application is rejected or rewritten | Request parity is gamed or copy edits inflate counts | Formal submissions count regardless of outcome; immaterial copy edits retain ID; material new requests increment: §4.3 |
| An unfinished second request is withdrawn and replaced by a third request for an experiment | Review is downgraded before its higher requirement is completed | A substantive replacement increments the sequence but inherits unfinished higher scrutiny for that application chain: §4.3 |
| AI writes three headings in one response | User participation and independent review are fictional | Actual first/third-round human contribution, genuine reviewer context, no simulated approval: §§2, 6.1 |
| User says they understand or prefer an option | Treated as approval; AI reasoning becomes the user's past reasoning | Debate → card → original teach-back → separated AI analysis/correction → second review and explicit decision: §6.3 |
| Accepted record must be immutable but outcomes arrive later | History is rewritten or outcomes never recorded | Freeze original body; append dated, authored result events; new linked decision for changed judgments: §8.3 |
| Approved, untested, and challenged are one status field | An approved but unverified choice cannot be represented | Separate decision, evidence, and lifecycle states while retaining required labels: §8.3 |
| Global skill and project copy share authority filenames | Template or another project's state controls execution | Explicit instance path and protocol/route/state versions; shared package remains unbound: §§9.3, 12–13 |
| Main file grows until a full reread is impossible | Summary-only reading silently replaces the hard rule | Archive raw reports and frozen history via links; retain full current route/state/rules; read through truncation or stop: §§9–10 |

## Policy alternatives that remain inactive

The following are genuine principle changes and have **not** been made. They are future review options, not blockers requiring a vote merely to finish this delivery.

| Existing rule and possible problem | Possible alternative | Benefit/cost trade-off | Current recommendation |
| --- | --- | --- | --- |
| Full reread each job may become costly | Structured delta/section reading after a verified baseline | Less reading, but missed constraints become more likely and require reliable change tracking | Retain full reread; consider only with actual repeated-work and reading-cost evidence and user approval |
| Fixed 10→7→5 and 5/+3 may fit some projects poorly | Outcome/risk/effort-based planning and limits | Better tailoring, less predictable hard stops | Retain values as initial policy; collect comparable experience before requesting change |
| Request parity is unrelated to actual risk | Risk-triggered review rather than odd/even sequence | Less arbitrary ceremony, but weaker predictable escalation and more discretionary classification | Retain odd/even policy now; any replacement must preserve anti-loop protection and receive approval |
| Required independent reviewer may be unavailable | Explicitly authorized self-review exception | Lower waiting cost, weaker challenge and greater correlated error | No automatic exception; disclose and keep the affected major decision pending unless the principle is explicitly changed |

Removing first-round user participation or own-word understanding checks would also be a principle change and is not recommended merely for speed. Existing user approval does not excuse AI evidence quality.

## Effectiveness validation plan

At adoption, use existing work-order and evidence entries to establish a small baseline. After two completed steps (no later than three), or two consecutive exhausted engineering-budget cycles, inspect repetition reasons, new-evidence production, decision delay, acceptance rework and administrative burden. Merge overlapping triggers.

Compare like work and state environmental differences. One failure is not evidence that the entire protocol is wrong; a small uncontrolled comparison is not causal proof of improvement. Two comparable checkpoints showing unhelpful overhead trigger a revision proposal, not automatic rule removal. Significant revisions use the same documented approval discipline.

No live project, model behavior guarantee, savings estimate, or application acceptance result is claimed in this delivery.
